4. human 的输入：类型与例子

把 human 的输入按“它让 agent 做了什么”分成六类。比例是粗略的，看例子更有用。

4.1 方向与范围：给目标和依据，不给实现

需要你去调研现在全球最好的英语学习平台和标准平台里面，单词学习的模式，我们需要考虑学校的效率和效果。#110，词汇天天练（10-23）
你给出一个详细的结论，我们系统来解决这个问题，而不是一点点的打补丁。#129，等级体系（11-05）

效果：agent 先写格式规约（docs/16）供审，再做样例，再全量。

4.2 具体的界面 / 交互指示：带截图、带规则

如果这个 part 里面的题目们有分数，则显示：得分/总分，比如“15/20”…如果没有算分，则显示：对的题目数/总题目数。#128（10-27）
这个 table 按照原本的样式直接显示在一个题目的页面上：有 emoji faces 的第三列变成一个下拉选项…#127（10-27）

最好执行的一类：有截图、有可验证的规则，还说明了“以后同类题都这样”。

4.3 质量标准：要求系统性、要求根因

看一下同类型的题是否，如果有问题，系统性的修复，而不是只修复这一个题。#126
同时检查一下，右边有多道题目聚合的情况，是否也有同样的问题，如果有就一起 fix。#92
这个问题需要重视…你需要去找到这个问题的 root cause，解决它。（附可能原因表）#131（11-05）

同类要求出现了至少 5 次，说明 agent 默认的修复范围偏窄（见第 7 节）。

4.4 决策与取舍

取消所有的 ASR 的输入，包括中文和英文，先把键盘输入做好。#116
这里的 emoji 都用黑白的 font emoji，不用图片彩色的。#127

以及平台冲突的裁决：ui-style-kit 的 1000px 缩放与 RC 响应式冲突，agent 列出影响（#62），平台给出决定后再接入。

4.5 流程与权限

需要 agent 先做 plan mode，跟我讨论和决策以下事项：现在的 bugs 很多是 agent fix 的…agent 可以自己做测试，所以对于一般的 issues，我们并不需要向提交人询问 ready 与否。#80（10-20）
等音频跑完后 push 并 deploy:dev，然后在 issue 里回复。对话（11-05）

4.6 澄清与纠偏

issue 里面的问题和建议是矛盾的，是只高亮首次出现的 words&expressions，还是都高亮。clarify 之后再提交。#93
这个问题还是没有 fix。#128（10-27、11-05 两次）

6. 做得好的地方

规则一次说清，长期生效

上表 10 条规则之后很少需要重复。在 GitHub 上下发的平台规范（#105–#107）也是一次同步到所有已有内容。

内容正确性有人兜底

55 个勘误 issue 都是“保持原书 → 提 issue → 人工确认 → 修改”，key 一直保持 reviewStatus: pending，agent 不自己升级为已审核。

先规约、后样例、再全量

新类型（KET、PET、词汇）都先写格式规约、做 1–2 个样例让人审，再批量生产。词汇从样例到 195 天全量用了 11 天。

agent 自测替代“问 ready”

#80 的决定：一般 bug 由 agent 跑单元测试、e2e 和三种视口截图，不再每次去问提交人；人只处理歧义和规则决策。

跨团队边界清楚

平台规范原文放在 docs/uniread-spec/ 不改写，我们的落实写在 docs/14；OSS 写入这类不可逆操作要后端书面确认，不由 agent 推断授权。

并行处理独立任务

11-05 把 main → develop 合并、OSS 工具改造交给两个子 agent，主线程同时排查音频根因、改记分，几小时内处理完 6 个 issue。

7. 摩擦与问题（有据可查）

修复在 main，验收在 develop：同一 bug 被报“没修好”两次

#128 的修复在 10-27 提交到 main，之后 9 天没有合到 develop。审核在 develop 预览站上看，仍然是红叉，11-05 再次报告。

根因双分支流程没有“main 的修复当天同步 develop”这一步，agent 汇报时也没说明修复在哪个分支、哪个站点能看到。

验证方式测不到要验证的性质：#131 反复三轮

第一次修复汇报“用语音识别回听过，内容完整”，但语音识别只认出单词，听不出重音和 /ə/、/æ/ 的区别。affect 在 SSML 正确的情况下仍读成 /ˈæfekt/，审核又报一次，human 要求找根因。

根因TTS 引擎把 CMU 的 AH0 读成全元音。11-05 用音素识别模型逐条测量才查清：旧音频中考 133/1,785、高考 439/4,263 条与原书音标不符。

修复范围默认偏窄

#92、#96、#124、#126 等 human 都要特别说“同类题一起查”。KET / PET 同题型一起修是在 10-20 写成规则之后才稳定执行的。

决定反复

10-20 当天“读写分成两个 item”（#71），几小时后又“合并，因为考试时这两部分时间是合并的”（#73）。约束（考试计时）在第一次决定时没有被提出来。

共用账号，分不清谁说的

human 和 agent 都以 Tuzibaobaobai 发言。审核同事和平台开发看不出哪句是负责人的决定、哪句是 agent 的汇报，复盘时也只能靠文风区分。

权限规则越来越细

“本地验证后要同意才推送”“审核同事的 issue 可以直接推生产”“develop 部署到预览站要确认”…规则正确，但散在记忆和 CLAUDE.md 里，只有 agent 看得全。

长任务卡住发布

11-05 重新生成约 1.5 万段音频要几个小时，human 两次在对话里问进度；推送、部署和 issue 回复都排在它后面。

审核积压：key 一直是 pending

819 个 item 的答案全部是 reviewStatus: pending。勘误一条条确认，但“整份 key 审核通过”没有对应的流程和负责人。

8. 案例：2026-11-05 一次处理 6 个 issue

human 的指令只有一句：“在 dev 上 fix github 上 milestone 11/15 的所有 assign 给我的 issues”。过程如下：

9. 改进建议

  1. 分支同步写进完成标准。main 上的任何修复，当天合并到 develop（或明确说明不需要）；agent 在修复汇报里写明“修复在哪个分支、在哪个站点可以验证”。可以加一个脚本检查 git log develop..main 是否为空，放进 npm test 或部署前检查。
  2. 验证证据要对准问题本身。汇报里写“测的是什么、怎么测的”，而不只是“测过了”。音频问题测音素和重音，布局问题给三种视口截图，判分问题给 e2e。测不到的部分直接写“需要人确认”。
  3. issue 模板加两栏。“验收标准（可验证）”和“是否适用于同类题 / 同类内容（是 / 否 / 待定）”。默认“是”，让系统性修复不必每次靠 human 提醒。
  4. agent 用独立身份发言。用 GitHub App 或机器人账号发修复汇报，或者至少在 agent 的评论开头加统一标记。负责人的决定和 agent 的汇报一眼能分清。
  5. 把记忆里的协作规则公开出来。推送 / 部署权限、勘误流程、分支规则从 agent 记忆迁到仓库里的一页（例如 docs/collaboration-rules.md），团队成员和平台开发都能看到、能改。
  6. 决定之前先列约束。涉及考试规则、平台对接、不可逆操作的决定，用 plan mode 先列约束和选项，再定（#80 已经这样做，效果好）。#71 / #73 的反复本可以避免。
  7. 长任务前置或拆开。预计超过 30 分钟的生成任务（音频、全量转录）放到前一晚或单独的分支跑；不影响的修复先推送部署，不必一起等。agent 在开始时给出预计时长和检查点。
  8. 给 key 审核建流程。确定谁审、按什么粒度（一天 / 一套卷）、在哪里记录，审核通过后由人把 reviewStatus 改为通过。否则 pending 会一直累积到上线前。
  9. 进度汇报统一格式。每次汇报固定说三件事：完成了什么（附证据）、还在跑什么（预计时间）、什么在等人（谁、做什么）。human 就不需要追问。
